## What this notebook teaches

**The hint decides the layout, the prompt decides the content.** Section 5 turns every photograph into a depth hint and
shows them side by side. Section 7 is a Predict → Change one thing → Run → Observe → Explain activity: the same prompts
and seeds are generated with a flat, a mismatched or the original hint, and the depth correlation with the original
layout is compared.

**It scores a generator without pretending a number is quality.** The held-out denoising loss uses each record's own
hint and identical noise before and after adaptation. CLIP scores are read against the real photographs, and depth
fidelity — the Pearson correlation and the scale/offset-aligned error between a generated image's estimated depth and
its hint — against a mismatched-hint baseline. The only assertions are the ones the procedure guarantees.

## Conformance notes

- **Standalone carrier (ST1–ST8, SRC4, SRC12):** no clone, repository install or repository import in the kernel.
  Section 2's carrier cell holds `CARRIED_FILES` — the package's four modules at their repository paths under `src/`,
  the stage runner, the lock as `requirements.txt`, the four snapshot manifests, the licence and a generated
  `source.json` (repository, revision, per-file SHA-256) — writes each into a fresh run directory and verifies it
  against `CARRIED_HASHES`, stopping on a mismatch. The carried text is the repository's, byte for byte (UTF-8, LF
  newlines), with no rewrites; the `weights` stage asserts each carried manifest against the package's pinned identity
  before staging.
- **Isolated environment (RUN1, RUN10, ENV1, ENV2, ENV6; §25.13):** no cell pip-installs into the kernel, and kernel
  cells import only the standard library, `IPython.display` and (for the BYOD upload) `google.colab`. The install cell
  downloads the `uv` 0.12.15 manylinux wheel by URL and refuses it unless its size and SHA-256 match, creates a managed
  CPython 3.12.12 virtual environment, and installs the carried lock with `uv pip install --require-hashes
  --only-binary :all:`. It removes Hugging Face tokens and the kernel's `PYTHONPATH` from the stage environment, sets
  `MPLBACKEND=Agg`, prints the environment's Python, `torch`, `diffusers`, `transformers` and `peft` versions and stops
  if CUDA is not visible there. `run_stage` runs one stage per process, streams its output to the cell and to
  `logs/<stage>.log`, and on failure raises a `RuntimeError` carrying the stage's own exception type and message.
- **Parity (PAR1–PAR4):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when a carried
  file, its hash, the carried lock or the manifests differ from the repository, when the lock does not pin every
  `pyproject.toml` pin or carries an unhashed entry, or when the notebook is not byte-identical to the generator's
  output. `tests/test_tutorial_stages.py` executes the generated carrier and `run_stage` code, and runs every stage on
  CPU against stubs (pre-flight only).
- **Stages (§4.1), one process each:** `weights` (stage and verify the four snapshots) → `prepare` (sample or BYOD,
  validation with refusal probes, the seeded split, recorded so every later stage rebuilds and re-checks the same
  records) → `encode` (depth hints and prompt embeddings written to two safetensors caches; the prior released) →
  `frozen` (held-out loss, CLIP and depth fidelity of the frozen model, the leave-one-out real-photo reference and the mismatched-hint
  baseline) → `activity` (the change-one-thing hint activity) → `adapt` (bounded LoRA fine-tuning, the trained
  in-memory model's test loss and a fixed-seed image recorded, `save_artifact`) → `evaluate` (`from_artifact` in a
  fresh process, the paired comparison) → `reload` (`from_artifact` in a second fresh process with parity against the
  recorded in-memory values, then the new prompt).
- **Model acquisition (MOD1–MOD9):** every snapshot is fetched only for absent entries, at a 40-character commit, and
  re-hashed before loading. The decoder safetensors come from the upstream repository's open, unmerged pull request #5;
  the notebook says so in its opening and in the exported provenance. The depth estimator is loaded by id and revision.
- **Guided layer (GDL1–GDL15):** audience and prerequisites, How to use this notebook, a roadmap with a fast path, the
  Input → Model/System → Output contract, observable learning objectives, a collapsible glossary, a prediction before
  each principal result, What to notice notes, collapsible Check your reasoning answers, the change-one-thing activity,
  Infrastructure-labelled collapsed setup cells (the runtime check, the carrier, the isolated install and the staging,
  each `# @title Infrastructure: …` with `cellView: form`), section types separating core concepts, evaluation
  practice and engineering, a troubleshooting table that covers the GPU, platform, disk, carrier integrity, the `uv`
  download and `uv venv` / `uv pip install` failures, failed stages and BYOD refusals with no row asking for a runtime
  restart, and a Conclude with evidence scaffold. Learner prose says "notebook" throughout.
- **Adaptation and evaluation (FT1–FT8, EVAL1–EVAL15):** LoRA on the UNet attention projections only, explicit
  hyperparameters, validation-selected epoch, held-out test used only for the final comparison, the frozen model as
  baseline, the leave-one-out real-photo reference (not a ceiling) and the mismatched-hint baseline as references, all
  metrics labelled sample-sanity.
- **BYOD (DAT10–DAT19, EXE1–EXE2):** `USE_BYOD` defaults to `False`; `BYOD_PATH` reads a zip without an upload dialog;
  the kernel passes the zip's path to the `prepare` stage, and user photographs get hints from the same estimator and
  flow through validation, adaptation, evaluation, export and reload. An invalid zip stops Section 4 with a
  `RuntimeError` that repeats the validator's refusal. The privacy note covers the layout information a depth map carries.
- `tools/validate_release_assets.py` performs source validation only. A release review must confirm a recorded clean
  run and a recorded conversion check in `docs/release-verification.md` before the status is promoted.
